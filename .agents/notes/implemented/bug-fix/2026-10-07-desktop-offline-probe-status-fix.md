# Agent Note: 修复桌面端公网模式连接状态与探针分流隔离

Status: implemented

## Problem

用户反馈桌面端在非局域网环境下，输入授权 Token 能够连接公网，但界面上所有“链接状态”均显示失败（全部红字报失败或超时）。

经对前后端探测链路排查，根因包含以下三点：
1. **未就绪时状态显示误判为连通失败**：
   在 `DashboardView.vue` 中，界面挂载时若代理总开关未开启（`!isRunning`），普通用户的 `userProxyRow` 仍显示旧记录或在测速未开启时最新点被判为“失败”；同时在开启加速前，常用站点探测并未展示“加速已停用/未就绪”置灰状态，而是直接被解释为网络失败。
2. **状态探测（probeSite）走本地引擎时的前置阻塞与回退陷阱**：
   `proxy_test_site_local` 要求本地引擎已启用（`ENGINE_ON`）；若总开关未开启，该接口直接返回 `error: "代理未启用：请先打开系统代理总开关"`。前端在将结果记入历史点后，若未细分错误类型，在状态判定上直接判定 `!point.ok`，在界面呈现出刺眼的红色“失败”而不是温和的“未开启/待就绪”状态。
3. **公网独立加速模式下的接口探针与端点解析失配**：
   在 `resolve_gate_url_for_iface` 中，当用户未在 Tailscale 或局域网内时，如果配置的令牌为通用公网授权令牌，`cf` 与 `vercel` 接口拨测可能尝试直拨不兼容或未启用的端点；此外，公网普通用户在未开启代理前无法直观看到隧道与网关的基础健康状态。

关联既有决策：
- 链入旧 ADR: [.agents/notes/implemented/bug-fix/2026-09-26-fix-multi-tenant-egress-probing-and-github-bypass.md](../../bug-fix/2026-09-26-fix-multi-tenant-egress-probing-and-github-bypass.md)（多租户出口测速收敛至有效端点）。

## Decision

1. **前端连接状态探测与未开启状态精细解耦**：
   - 在 `desktop/src/views/DashboardView.vue` 中，当代理总开关未开启时，连接状态区明确显示“待就绪（请先开启加速）”或“已停用”，状态文字与柱条颜色使用 muted 柔和中性色，彻底禁止显示红色的“失败”或错误延时。
   - `testUserProxyRow` 在代理未开启时直接重置或跳过拨测，不在未开启时写入失败历史记录；对于历史记录中残留的“代理未启用”错误点予以自动清洗过滤。
2. **站点探针本地引擎拨测错误归一化**：
   - 在 `desktop/src-tauri/src/lib.rs` 的 `proxy_test_site_local` 中，当 `ENGINE_ON` 未置位时，返回明确的 `status: "not_running"` 标记，便于前端精准区分“代理未开启”与真实的“出网链路失败”。
3. **公网 Token 模式下的默认出网隧道与探测保障**：
   - 强化用户输入 Token 后的默认链路行为：只要录入合法 Token（无论是否以 `usr_live_` 开头），在 Direct 模式下默认确保端到端长连接直接与公网原生 VPS 网关（`wss://rn.ponygo.fun/ws`）建立安全隧道通信，不依赖任何局域网组件。

## Alternatives considered

- **在代理未开启时依然让 probeSite 绕过本地引擎直连探测**：被否决。因为在非局域网环境下，直接在本地向 `google.com` 发起 TCP 连接必然被 GFW 阻断或超时，依然会导致全部变红，且违背了“前端状态代表真实代理能力”的原则。
- **强制在进入首页时自动开启系统代理**：被否决。改变系统全局网络配置必须由用户显式触发或在配置完成后由流程引导确认，自动静默强开会侵犯用户网络掌控权。

## Consequences

- 桌面端在纯公网环境下输入授权 Token 后，加速开关未开启时状态呈现为清晰的待命状态；开启后经由公网隧道准确测得毫秒级延迟，不再出现假红和误报失败。
- 所有单元测试保持全绿通过。
