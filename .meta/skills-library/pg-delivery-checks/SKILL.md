# pg-delivery-checks —— 外发前选证

**项目等价命令约定**：文中 `<项目测试命令>`、`<项目类型检查命令>`、`<项目文档门禁命令>`、
`<项目链路检查命令>`、`<项目 PR 状态命令>` 只是占位。
安装到某项目后，先读该项目的根常载文件、任务脚本/包清单/Makefile 与 CI 配置，把它们替换成真实入口；
替换后的真实命令必须原样进报告，不得只报占位名。

## 真相源

- 项目的根常载约定文件与贡献指引 —— 本地钩子的**真实边界**（哪些检查本地已有，哪些归 CI）。
- 项目的测试策略文档 —— 证据种类与分层（单元 / 集成 / 快照 / 端到端 / 真实外部依赖）。
- 项目的 CI 配置 —— 全量覆盖与平台矩阵的归属。**全量是 CI 的职责，不是本地的默认动作。**
- 活动决策记录 —— 哪些检查是某一决定刻意保留的（别把刻意义务当可跳过的开销）。

## 步骤

1. **确认检出与基线**：`git status --short --branch`、`git rev-parse --show-toplevel`。
   基线 ref **只能核实、不能猜**：从远端或栈状态读当前 PR 基线/父层，`git fetch` 后再
   `git diff --stat <已核实基线>...HEAD`。合并了变动的基线之后，重跑范围报告、重新评估受影响行为，
   只重跑被这次合并无效化的检查。
2. **按变更面选最小证据**（每条都给"会因该回归而失败"的最窄检查；更广的只补 diff 实际触达的面）：

   | 变更面 | 首选证据 |
   |---|---|
   | 包/脚本/模块行为 | `<项目测试命令> <所属测试文件>`，必要时加聚焦用例名过滤 |
   | 共享契约（类型/签名/导出） | 涉事包测试 + `<项目类型检查命令>` |
   | 生成物（清单、声明、快照） | 再生成 + 该生成物的新鲜度/一致性检查 |
   | 文档、决策记录、被文档引用的注释 | `<项目文档门禁命令>`（链接、格式、配对、预算） |
   | 面向用户或模型可见的输出（CLI 文本、UI 文案、诊断） | 拥有该输出的聚焦快照或可运行示例 |
   | 清单/构建配置/入口/构建产物路径 | 构建 + 卫生检查 + 该产物的冒烟 |
   | 真实外部服务行为 | 对应端到端目标（凭据可用时）；**永不打印密钥** |
3. **每个选中的检查都补齐证据链四件套**：① 受影响面的 owner（文件/模块/契约）；② 会失败的
   producer/consumer 路径（谁产出、谁消费、回归从哪条路可见）；③ 覆盖清单与不覆盖清单；
   ④ 最强反方——"为什么这次不需要更广的检查"。回答不了 ④，就说明该跑更广的范围。
4. **不重复已验证的检查**：检查已通过后，不因"紧接着要提交/推送"再跑一遍；尤其不要为了重复
   本地已有的推送前钩子而手动跑它。重复执行不是更强的证据，只是更贵的证据。
5. **覆盖率作用域与测试过滤是两件事**：测试文件过滤选"跑哪些测试"，覆盖率作用域另需点名
   受影响源文件/模块。不要为了让未覆盖面消失而放宽阈值、加"无测试即通过"开关或缩小源作用域。
   依赖图工具找不到只经配置、动态加载、子进程、worker、构建产物或外部服务触达的行为 → 显式点名。
6. **何时才跑全量**：用户明确要求、正在定位 CI 失败、或变更横跨仓库使任何窄集都不可信。
   现有任务脚本与 CI 配置就是清单，不要凭记忆重建一个聚合入口。
7. **历史重写型推送**：重写后旧提交哈希、行内评论锚点、评审结论都不是现行证据，必须重审。
   发布前记录远端分支**确切 OID**，用带租约的强推 `--force-with-lease=<branch>:<observed-oid>`；
   裸 `--force` 永不允许。若所用工具把"取回 + 级联重写 + 发布"合成一个不可插入验证的动作：
   运行前要求工作树干净、记录官方层序与远程头；返回后逐层重查远程头、逐层对比实际基线重选证据，
   全部通过前**保持未合并、验证状态报 pending**。工具返回 0 不等于栈就绪。
8. **失败处理**：相关检查在普通推送前失败 → 停下修复或说明阻塞，不要"先推再看 CI"。看起来是
   环境特异性失败也要证：记录确切命令、失败用例、平台差异，确认非平台证据，优先修不确定行为。
   绕过本地钩子只在用户明确同意时，并报清失败内容与 CI 为何被预期为不同。

## 校准样例

- 正例（窄证据足够）：给某导出函数加默认参数、只影响一处调用 → 所属测试文件 + 类型检查；不跑全量。
- 反例（重复劳动）：全量套件刚绿，只因为要执行提交就再跑一次；更强的证据并没有增加。
- 反例（全量凑齐）：改了三条注释就要求全量套件"稳妥"——用覆盖面换安心，换不来更强的证据。
- 正例（四件套齐全）：删掉一个配置路径 → owner=配置加载器；路径=加载器读键 → 运行期消费点；
  消失清单=该键的解析分支与其测试；保留清单=旧键的兼容转换；最强反方="外部用户可能仍写旧键"，
  故保留兼容层只删内部默认值。
- 正例（重写型推送）：重写分支后记录远端 OID 并用 `--force-with-lease=branch:<oid>`；并发更新时推送中止即为正确行为。
- 反例（裸强推）：`git push --force` 覆盖协作者的提交——不可恢复，且无租约可救。
- 正例（无检查上报的诊断顺序）：平台报"无检查"时先读可合并性状态；冲突状态下平台本就不产生这些运行，
  用 `git merge-tree --write-tree HEAD origin/<base>` 确认冲突路径。
- 反例（用空提交等信号）：连推空提交、草稿与就绪反复切换、revert 再恢复——历史变脏，信号依然为零。
- 边界（靠 review）：把"该不该跑全量"交给"变更是否真的横跨仓库"这一判断；判据是触达面，不是文件行数。

## 验证与报告

- 每条选中检查跑**一次**，报告里贴：占位替换后的真实命令 + 观察到的结果（含选中用例数，
  别把被过滤到 0 条的运行当聚焦证据）。
- 远端一致：`git rev-parse HEAD origin/$(git branch --show-current)` 两行相同；平台侧用 `<项目 PR 状态命令>` 读检查状态。
- 状态词只允许三档：通过 / 待定（pending）/ 失败。待定就报待定；不把重试、跳过、待定的 CI 说成通过。
- 环境特异性失败：报确切命令、失败用例、平台差异、以及"CI 为何被预期不同"。
- 重写型推送：附后置验证清单（逐层范围、逐层证据、合并状态），并显式说明"未合并直到全部通过"。
