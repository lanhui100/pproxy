# pg-gc-agent-notes —— 决策记录语料回收

目标是**减少活动语料而不擦掉仍能指导工作的历史**。每条都按语义判：字数与年龄只是发现候选的
线索，永不作为判定标准。也不允许"为凑配额而归档"。

**项目等价命令约定**：文中 `<项目归档封印命令>`、`<项目归档校验命令>`、`<项目文档门禁命令>`、
`<项目配对重录命令>` 按被安装项目真实入口替换（本框架实例通常为 `.meta/gates/archive-verify.sh` 的
`seal` / `check` 位置子命令）；替换后写进报告。

## 真相源

- 决策记录规则（`notes/README.md` 之类或 `.agents/notes/AGENTS.md`）—— 路径两轴、骨架、触发规则、判据。
- 归档区规则（`archived/AGENTS.md` 之类）—— 冻结语义与 manifest/封印契约。
- 当前代码、配置、派生清单、更新的决策记录、入链 —— 判断某条理由是否仍在拥有或约束什么。
- 各 lifecycle 的现行骨架要求 —— 归档/migrate 时标题时态必须与目录一致。

## 步骤

1. **读契约再判断**：先读上面四类真相源，尤其"何时该写一条"的创建判据；不要在没读现行骨架时动手改标题。
2. **新增时必做取代检查**：起草一条新记录，就触发一次**限定范围**的活动语料审计（同决策 / 同机制 /
   同被否替代）。逐条分类：完全取代 → 同一变更内处理旧条；部分取代 → 两边交叉链接、都保留；
   独立有用的理由 → 保留；已过时的提案 → 否决；不再能拦住真实误判的 rejected → 删。
   新记录若吸收了旧条的全部独有命题 → 按合并规则并入，**不把已知命中推给以后的全语料审计**。
3. **按未来价值分类**（先判生命周期，再判价值）：

   | lifecycle | 处置 |
   |---|---|
   | implemented | 只描述小 UI 调整或纯机械改动的整条**删**（并修/删入链）；理由、备选、负向保证、持久/线协议语义、归属边界、安全规则、重新引入条件仍可能指导未来 → **留活动**；实质历史决策已完成且不再指导工作、但历史理由仍值得留存 → **归档** |
   | proposed | **永不归档**：还有价值就留活动；不再值得推进就以诚实理由改为 rejected 并满足 rejected 骨架 |
   | rejected | 只作为护栏保留：落选方案仍是**诱人的、有意义的错误**、且本条说清了为何落选 → 留；想法已过时/已被取代/不再可信/拦不住重新争论 → **整条删**（并修/删入链） |

   判**决定**本身而不是它的实现机制：一次机械改名或类型抽取，也可能记录下长期的命名、兼容或归属规则。
   长度不是判据；"实现完了"也不构成删除理由。小 UI 与纯机械的删除判据**先于**留/归档判断执行。
4. **归档一个已实施条目**（按项目实际形态；有双语与配对记录时是"正文 + 对照语言 + 配对记录"三件套）：
   ① 把整组文件从 `implemented/<kind>/` 移到 `archived/<kind>/`（路径里**故意不再有** `implemented`
   段，保血缘用移动而不是复制+删除）；
   ② **正文一字不改**，只在 `Status:` 行下方插一行 `Archived: YYYY-MM-DD`，两侧语言用同一个日期；
   ③ 只为这两处元数据改动机械重录配对哈希；不翻译、不重排、不更新事实、不修区内链接
   （既有标题标点、空行布局、语言切换文案都保持原样，它们是归档对象不是待改项）；
   ④ 搜活动散文中指向它的入链：改为指向现行权威，或仅在"刻意引用历史快照"时改指归档路径，否则删掉；
   **永不**从归档件向外修链；
   ⑤ 跑 `<项目归档封印命令>`（追加式：先证明既有每个封印仍匹配，再只为新条目追加哈希），
   随后跑 `<项目归档校验命令>`（只读比对，应 `exit 0`）。
   封印后：永不编辑、移动、翻译、重排或删除该条目；它仍是合法的入链目标，但只作历史快照，不作现行权威。
5. **状态轴不许失真**：未实施的记录不进 `implemented/`；标题时态必须与目录一致（提案用将来时标题，
   迁移到已实施时改成现在时并把验收/风险折进后果节）；多类混装的记录要拆条，别让一条记录同时宣称
   "已落地"和"仍在设计"。

## 校准样例

- 正例（删）：已实施的"折叠侧栏控件"——小 UI 行为、已关闭、无人会再引用；整条删并清掉入链。
  反例（当保留理由的是长度）：因为一条记录很长就保留，或因为另一条很短就删——长度不含决策价值。
- 正例（留）：单一主目录解析器——跨产品的归属规则，未来任何"再加一个家"的提案都要被它约束。
  正例（留到条件解除）：被丢弃的图像内容块——只有在多模态支持落地时才该重新引入，这个协同条件本身就是理由。
- 正例（留 rejected 作护栏）：合并某两个包的提案——"合并更省"的诱因仍在，落选理由仍然有效。
  反例（删 rejected）：某条 rejected 的前提（旧协议/旧 UI）已不存在，留着只是让读者以为问题还活着。
- 反例（proposed 归档）：把还有价值的活提案扫进归档区——归档区只读，提案就此失活，等于悄悄否决了它。
- 正例（部分取代）：新记录承接了旧条的核心决定但旧条另有"安全边界"命题 → 交叉链接、都留。
  反例（多余地重录）：为保留候选数而新建一条重复记录，而不更新既有的 owner。
- 反例（归档时改正文）：顺势把归档件里的过时事实"修好"——破坏冻结即法律，且封印会立刻报哈希不符。
- 边界（靠 review）：机械改名类记录——决定本身就是命名规则时留，纯重排无规则时删。

## 验证与报告

- 跑 `<项目归档封印命令>`（如本次有归档）与 `<项目归档校验命令>`，再跑 `<项目文档门禁命令>`、
  `git diff --check`；有双语配对时跑 `<项目配对重录命令>` 并确认配对状态干净。
- 报告逐项清点：活动已实施记录 保留 / 删除 / 归档 各几条，rejected 保留与删除各几条，
  proposed 是否改为 rejected，以及**每一个真实边界个案**的处置与理由。
- **不要声称归档件的出链有效**：归档校验器故意不检查从冻结区向外的链接；能报的只有"入链已重定向且校验通过"。
- 不得用"已归档 N 条"当成果指标；报告要给判定依据（哪条命题不再指导工作 / 哪条仍约束未来）。
