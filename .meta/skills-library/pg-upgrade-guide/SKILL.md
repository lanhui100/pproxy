# pg-upgrade-guide —— 破版迁移指引

迁移指引回答一个问题：**正在跑 vT 的人，要改什么才能跑下一个版本。** 它写在引入破坏的**那次变更里**，
一经识别就写，不延到发布准备阶段。

**项目等价命令与位置约定**：文中 `<项目迁移指引校验命令>`、`<项目配对重录命令>`、`<项目链接检查命令>`
是占位；推荐的家是 `docs/upgrade-guide/v<version>/<item>/guide.md`，若项目已有迁移/升级文档目录，
改用项目等价位置并在报告里写明实际路径。

## 真相源

- 项目的文档标准 —— 迁移指引的 kind／骨架／篇幅上限归它，本文不复制具体数值。
- 引入破坏的那次变更本身（diff、相关决策记录）—— 旧行为、新行为、受影响者只能从这里取。
- 项目既有的迁移指引与校验脚本 —— 格式门禁与最大篇幅的**唯一口径**。
- 发布版本的事实来源（根包清单的版本字段或等价物）—— 决定 `<version>` 目录归谁。

## 步骤

1. **判范围：只写仓库外可观察的破坏**。典型清单：命令行与旗标、配置键及其可接受值、
   持久化的用户数据（日志、数据库、用户目录）、SDK 导出与线协议消息、已发布包的名称与入口。
   **不写**：预稳定内部接口，且其消费者在同一次变更里全部更新完。持久格式的破坏另有类型确认流程时，
   指引只写读者要做的动作，并链到那份记录。
2. **定位置与命名**：`docs/upgrade-guide/v<version>/<item>/guide.md`。
   `<version>` 取**写指引时**的根版本字段（指引描述"从该发布到下一个发布"）；
   `<item>` 用被破坏面的 kebab-case 名（如 `profile-flag-rename`）。
   每个 item 目录只放：正文、对照语言版（若项目有双语）、配对记录；不放索引、不放附件。
3. **维护规则（不是一次性写作）**：根版本未变期间，当前版本目录描述"从 vT 到当前主干"的增量；
   后续变更触到某条已覆盖的面 → **同一次变更内更新那条指引**；破坏被回滚 → 删掉指引。
   版本提升后，旧版本目录冻结；新破坏进新版本目录。**一条指引永不跨两个发布。**
4. **写 `Change`**：旧行为、新行为、谁受影响（按角色或使用形态点明，不按文件点明）。
   读者要能一眼判断"这条命中我了吗"。
5. **写 `Migration`**：有编号的步骤，点名确切文件、键、命令或符号；结尾给出**如何确认迁移成功**
   （可执行的观测，不是"应该没问题"）。机械重复的步骤收敛成脚本或一条项目命令，由指引调用。
6. **压篇幅**：超限时的去处是——外链到源码/符号而不是复述代码；把理由移进决策记录；
   把重复步骤变成脚本。**不**靠删掉失败模式、限制或所有权来瘦身。
7. **双语与配对**（若项目有此约定）：同一次变更里写对照语言版，按项目配对规则重录，别手改配对记录文件。

## 校准样例

- 正例（该写）：配置键 `profile.default` 改名为 `profile.name`，且旧键不再被接受 →
  指引写明旧键/新键、逐条迁移步骤、确认命令（读一次解析后的生效配置）。
  反例（不写）：把某个内部预稳定模块的导出改名，且同一次变更内更新了全部调用方——仓库外无人可见。
- 正例（受影响的角色写清）：破坏命中自建插件作者而非普通用户 → `Change` 点名"自建插件作者"，
  并给出插件的等价改法。反例：只写"接口有变"，读者无法自查命中。
- 反例（把理由塞进 Migration）：在步骤里解释"为什么决定重命名"——理由归决策记录，步骤只留可执行动作。
- 反例（一条跨两版）：v0.3 目录里的指引同时描述 v0.2→v0.3 与 v0.3→v0.4 的改动——读者无法确定自己处在哪一段。
- 正例（回滚即删）：破坏在发布前被回滚 → 同一变更内删掉指引，而不是留着当"历史记录"。
- 正例（确认步骤可执行）：迁移后运行 `<项目配置校验命令>`，观察输出中新键有值、旧键不再出现。
  反例：只写"确认一切正常"——不可验证的确认等于没有确认。
- 边界（靠 review）：同一发布里两个相邻破坏是否该合成一条指引——判据是读者能否独立完成迁移；
  能独立完成就分条，耦合步骤才合一。

## 验证与报告

- 跑项目机械门禁并贴输出：`<项目迁移指引校验命令>`（骨架、字段、篇幅）、
  `<项目链接检查命令>`、`git diff --check`；有双语则跑 `<项目配对重录命令>` 后确认配对状态干净。
- 逐条走一遍指引记载的迁移步骤（至少在一个临时/沙箱环境中执行），确认"确认步骤"的观测真的会出现；
  跑不通的步骤必须修指引，而不是改期望。
- 报告：指引路径、被破坏的面、受影响角色、确认迁移成功的那条命令、实际跑过的校验命令与结果。
- 不得把"指引已写"等同于"迁移已验证"：未执行过的步骤要显式标注为未验证，并点名验证 owner。
